# 四人分工与协作

采用按系统区域分工：**A 管小程序，B 管业务闭环，C 管 AI，D 管平台与后台。**

这份分工取代此前“每人做一部分小程序和后端”的方案。目录与文件清单见 [文件归属](11-file-ownership.md)。

## 1. 总览

| 成员 | 独占代码范围 | 主要交付 |
|---|---|---|
| A | miniprogram/ | 所有学生端页面、组件和 API 调用 |
| B | modules/business/ | 信息、线索、认领、归还、站内通知 |
| C | modules/intelligence/ | AI、匹配、任务执行与评测 |
| D | modules/platform/、common/、admin-web/、deploy/ | 身份、文件、管理、工程和部署 |

这里 modules 的完整前缀是 `backend/src/main/java/com/campus/lostfound/modules/`。

“独占”指主维护责任，不禁止互相评审。跨范围修改先与负责人协调，不能把一个页面长期拆给多人维护。

## 2. A：整个微信小程序

### 负责什么

- 首页、发布、详情、编辑、我的发布。
- AI 草稿确认与推荐结果页面。
- 线索、认领、交接、消息页面。
- 我的、资料、举报。
- 公共组件、导航、请求、上传交互、登录交互与任务轮询。

### 向别人要什么

| 提供者 | 交付给 A |
|---|---|
| B | 业务接口、状态与失败示例 |
| C | AI/匹配接口、排队与降级示例 |
| D | 登录、上传、私密图片许可、字典接口 |

A 不实现 Java 业务。B/C/D 不直接拆写 A 的小程序组件。

### 验收

真机能完成业务流程；无图、AI 失败、切后台等状态可理解，草稿和任务能够恢复。

## 3. B：完整业务闭环

### 负责什么

- post：正式信息、确认特征、搜索、状态服务。
- recovery：私密线索、证明、申请、交接与归还。
- notification：站内通知、未读、去重。
- 对应数据表、迁移、业务接口和自动化测试。

信息与申请状态由同一人维护，接受、撤销、归还等事务不再跨人分割。

### 与其他区域的边界

- 使用 D 的身份、文件与幂等基础能力。
- 发布时调用 C 的 JobService 入队，不同步调用模型。
- 向 C 提供只读 PostQueryService 和 NotificationService。
- 向 D 提供下架等业务工作流；D 不直接改认领表。

### 验收

无 AI 也能从发布走到归还；并发时最多一人被接受；私密信息、状态与通知正确。

## 4. C：AI、匹配和任务整体

### 负责什么

- ai：文字/图片草稿、模型适配、文本向量。
- matching：候选、规则评分、混合排序、理由、版本。
- job：任务入队、调度、租约、重试、恢复与处理器。
- AI 表、任务表、迁移、测试、固定样本评测。

通用任务框架和 AI handler 都由 C 维护，不再拆给 D。

### 与其他区域的边界

- A 开发 AI 界面，C 返回草稿、任务状态和推荐结果。
- B 保存用户确认后的特征，C 不覆盖正式信息。
- C 通过 B 的只读服务取候选，通过通知服务创建消息。
- C 使用 D 的文件读取能力和服务器配置，不读取私密证明做公共匹配。

### 验收

真实服务可用，规则降级有效，任务重启可恢复，旧结果不覆盖新版本，评测有证据。

## 5. D：平台、管理端与工程

### 负责什么

- identity：微信登录、平台会话、权限、账号状态。
- asset：上传、归属校验、存储、私密访问许可。
- moderation：举报、字典、管理查询、统计和操作日志。
- common：统一返回、错误、幂等基础实现。
- 整个 Vue 管理端、后端构建与部署。

D 初始化工程和公共配置，B/C 自己完成模块实现、迁移与测试。D 不承接 AI 任务框架。

### 验收

真机登录上传、账号权限、文件许可、管理后台和部署可用，数据与文件能恢复。

## 6. 对接顺序

| 提供方 | 能力 | 调用方 |
|---|---|---|
| D | 身份、文件、字典、统一错误 | A、B、C |
| B | 信息与恢复业务 API | A、D |
| B | 只读候选查询、站内通知服务 | C |
| C | JobService 入队 | B |
| C | AI、匹配 API | A |
| B/C/D | 接口示例与安全错误码 | A |

JobService 只负责落库，不依赖具体 handler。PostQueryService 只读，不依赖入队。

避免把发布和匹配塞进一个互相注入的大 Service。后台调度再调用处理器，查询与命令分离，避免 Bean 循环依赖。

## 7. 工作量与协作规则

A 先做共享表单、列表、详情和状态组件，减少页面重复。B 先完成规则业务流程。C 与 D 在第一阶段验证外部服务和运行环境。

初版管理后台优先实现必要管理功能，暂不复杂美化。

每个接口交付：路径、字段、权限、状态、错误码、成功与失败示例。A 可先接固定示例，随后切真实实现。

每人负责自己的测试；A 组织学生端联调，B 组织业务闭环验收，C 组织 AI 评测，D 组织部署验收。

## 8. 公共文件谁最终合并

| 文件 | 主维护人 |
|---|---|
| 小程序 app.json、样式、工具与构建 | A |
| 后端 pom.xml、启动、公共配置 | D，B/C 提供依赖需求 |
| Flyway 迁移编号 | D 协调，B/C/D 各写自己区域脚本 |
| 接口文档 | B/C/D 各维护自己的接口，A 提供使用反馈 |
| 总体需求与架构 | 四人共同确认，目录归属以本文件为准 |
