本仓库为《校园失物招领与线索匹配平台》软件设计成果仓库，包含完整的架构设计、系统设计、接口契约、数据约束、验证证据与团队分工。

## 1. 项目简介

- **项目名称**：校园失物招领与线索匹配平台
- **设计版本**：SD V1.2
- **基线需求**：需求分析 V1.2（逐字副本见 `baseline/需求分析文档_V1.2.md`）
- **技术选型**：模块化单体 + PostgreSQL + Python Web/SQLAlchemy + 同源 Web + 私有图片存储
- **核心原则**：相似度仅提供线索，不认定所有权；双方确认才构成归还。
- **范围**：校内发布、线索检索、人工核验、双方交接、争议治理。
- **不包含**：公开聊天、支付、物流、GPS、人脸识别、图像识别、大模型确权、跨校匹配。

## 5. 接口与状态约定

### 5.1 接口统一约定

- 根路径：`/api/v1`
- JSON：camelCase；ID 字符串；时间 ISO 8601 带时区。
- 成功：`{ "data": {...}, "requestId": "uuid" }`
- 错误：`{ "error": { "code": "...", "message": "...", "retryable": false, "details": {} }, "requestId": "uuid" }`
- 写接口：必须带 `requestKey`；HTTP `Idempotency-Key` 与 JSON `requestKey` 相等。
- 权限：服务端从会话推导 `userId`/`campusId`，不信任前端传值。
- 状态码：400 VALIDATION、401 UNAUTHENTICATED、403 FORBIDDEN、404 NOT_FOUND、409 CONFLICT、429 RATE_LIMITED、503 TEMPORARY_FAILURE。

### 5.2 状态流转

- **记录**：OPEN、RESERVED、RETURNED、WITHDRAWN、EXPIRED。`hidden`/`frozen` 为独立管理标志，不属于业务状态，不暂停时钟。
- **认领**：PENDING、SELECTED、REJECTED、INVALIDATED、CANCELLED、TIMED_OUT、COMPLETED。
- **规则**：
  - 不允许认领自己发布的信息。
  - 同一用户不能对同一信息重复提交有效申请。
  - 接受一个申请时，招领信息进入 RESERVED，其他申请保留等待。
  - 归还完成时，其余未处理申请自动结束。
  - 接受申请必须有事务和并发校验，20 并发只能一笔成功。
  - 记录完成、关闭或下架后，不能再产生新认领申请。

## 6. 开发顺序

1. **第 1 阶段：共同定稿**四人共同确定字段、状态、接口、页面草图和演示流程。
2. **第 2 阶段：独立开发**A：发布、列表、详情、媒体；B：规则匹配、AI 草稿、候选任务；C：线索、认领、交接、消息；D：工程、登录、文件、基础数据、治理、清理。
3. **第 3 阶段：业务联调**A：详情与编辑；B：语义匹配与推荐解释；C：消息与归还；D：管理后台、举报、统计。
4. **第 4 阶段：验收交付**
   A：前端整合；B：匹配效果评测；C：全流程验证；D：部署与后台整合。

## 7. 验收场景

1. 失主没有照片，文字描述能匹配到带图片的招领信息。
2. AI 提取错误时，用户修改后可以正常发布。
3. AI 服务失败时，可以手动发布并使用基本搜索。
4. 两人同时认领同一物品，只能有一份申请被接受。
5. 其他用户无法读取认领证明、私密线索和交接联系方式。
6. 物品归还后，相关信息退出正常匹配，关联状态同步更新。
7. 隐藏/冻结/注销后，首个新请求不得返回私密字节。
8. 备份恢复后，已删除对象不可复活。
9. 真实 5 人试用与无障碍走查未执行就保持空表，不得伪造通过。
